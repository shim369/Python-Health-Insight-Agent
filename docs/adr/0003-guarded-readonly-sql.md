# 0003: 自由SQLは多層防御とユーザー絞り込みの強制

- 状態: 採用

## 背景
型付きツールで答えられない集計のため、LLMにSQLを書かせたい。一方、LLMが書くSQLは更新・削除・
他ユーザーの閲覧・長時間クエリ・情報漏えい(メールアドレス等)のリスクがある。

## 決定
複数の層を重ね、どれか1つが破られても止まるようにする。

1. **構文解析(sqlglot)**: SELECT系の1文のみ。複数文・DML/DDL・`SELECT INTO`・`FOR UPDATE`・
   `COPY`/`SET`/`EXPLAIN`、CTE内のDMLを拒否。
2. **許可リスト**: 参照可能なテーブルは明示した8表のみ(`users` は除外)。`information_schema`/`pg_catalog`/
   他スキーマを拒否。危険な関数(`pg_sleep`, `pg_read_file`, `dblink`, `set_config`等)は名前で拒否し、
   未知の関数は許可リスト方式。
3. **ユーザー絞り込みを「書かせる」のではなく「強制する」**: すべての表参照を、呼び出しユーザーの
   行だけを返すサブクエリに書き換える(子表は親を介して)。LLMのSQLが `OR true` や他人のIDを書いても、
   他ユーザーの行には届かない。CTE名が表名と衝突するクエリは、すり抜け防止のため拒否。
4. **READ ONLYトランザクション + `statement_timeout`/`lock_timeout`**。
5. **行数上限**をLIMITの注入で強制(既存LIMITが小さければ尊重)。結果は文字数でも切り詰める。
6. **読み取り専用のDBロール**(`health_insight_reader`、マイグレーション0002)。`users` にSELECT権限を与えない。

## 結果
- 「user_idの絞り込み必須」を、検査(漏れが起こり得る)ではなく書き換え(構造的に漏れない)で満たす。
- 危険な文が通らないテストを大量に持つ(88件のガード単体 + DB上の結合テスト)。
- 書き換えにより、LLMには生SQLと異なるSQLが実行される。透明性のため、LLMの元SQLを結果に残す。
- sqlglotの解釈と、PostgreSQLの実際の解釈の差が理論上は残る。だから4〜6の層を別に持つ。
